# Saturn roadmap

Обновлено: **2026-09-25**. Основание: обсуждение Saturn Mobile, совместной работы,
монтажа, пространственного контекста и проектирования по документам.

Это единый план развития Saturn IDE / Cloud / Mobile / Agent. Пункты ниже —
**запланированные возможности**, а не заявление об их реализации. Закрывать пункт
можно только вместе с реализацией, проверками и ссылками на результаты.

Действующие границы задаёт [архитектура](docs/architecture.md), обязательства переноса —
[матрица возможностей](docs/capabilities.md), область уже описанных проверок —
[verification](docs/verification.md). Этот roadmap дополняет их, не отменяет незавершённый
перенос и не меняет архитектурный контракт одним лишь появлением задачи.

## Направление продукта

**Saturn Mobile — новое поколение средств разработки: вайбинженеринг.**
Инженер описывает намерение, работает с живой моделью голосом, текстом и прикосновениями,
совместно с участниками проекта и Saturn Agent проверяет результат и подготавливает
изменение программной части инженерного объекта. Телефон — полноценная среда этой работы,
а не только просмотрщик уведомлений или уменьшенная desktop IDE.

Одна типизированная инженерная модель связывает исходники, оборудование, топологию,
сигналы, HMI, отчёты, среды исполнения и наблюдения. Человек выражает инженерное решение
один раз; повторный перенос уже известного смысла между независимыми настройками
должен исчезать. Агент использует эти связи, а не вручную обслуживает несколько моделей.

**Ближайший приоритет — коллаборация участников и агента.** Камеры и видеорегистраторы
подключаем как существующие источники наблюдения. Непрерывная запись и основной архив
остаются на их стороне. Коллаборация не ждёт собственного видеосервера, полного BIM
или сложной 3D-модели здания.

## Неизменные границы

- Один authored TypeScript project; оборудование, диаграммы и AI не получают отдельные
  редактируемые Project/Signal/Topology. Всю систему разрешено описать в одном файле
  или разделить обычными imports: правила «один файл — один прибор» нет.
- Голос, чат, drag и исходники изменяют один проект через общие типизированные операции.
  Новый публичный примитив вводится вместе с работающим сценарием, а не каталогом
  сущностей на будущее. Существующие equipment/ports/signals/presentation переиспользуются.
- Source, checked, published, applied и наблюдаемое состояние различимы.
  Сообщение «я подключил», ответ устройства, визуальное наблюдение и инженерная проверка
  сохраняют своё происхождение. Applied revision не доказывает правильность монтажа;
  confidence агента не заменяет доказательство. Это разные измерения, не лестница истины.
- Разработка, публикация, оперативное управление, просмотр видео и передача кадров агенту
  имеют отдельные полномочия. Переключение роли или вида интерфейса не меняет права.
  Открытие чата не выдаёт агенту runtime credentials, shell или полномочия apply.
- Обсуждение, alarm, команда и изменение проекта имеют собственные жизненные циклы.
  Закрытие обсуждения не квитирует alarm; согласие в сообщении не применяет сборку.
- Live-команды проходят runtime authority с проверкой среды, актуальной applied revision,
  прав и результата. Неоднозначный ответ не ретраится как обычное сообщение.
  Replay, симуляция и восстановление мобильной связи не отправляют команды объекту.
- Общая дизайн-система и domain-компоненты используются в Shell, чате, карточках событий,
  отчётах и HMI. UI агента не должен становиться отдельным продуктом.

## Порядок и зависимости

Сначала закрывается один сквозной сценарий совместной работы. Расширения добавляются
к тому же основанию; даты релизов и неподтверждённые оценки сроков здесь не назначаются.

| Этап | Результат | Зависимости |
| --- | --- | --- |
| COL-1 | Участники, долговременные обсуждения, точные ссылки на контекст | Существующая модель ресурсов; серверная авторизация |
| COL-2 | Совместные сеансы, присутствие, показ на дисплеях | COL-1; текущие представления Shell |
| AGT-1 | Агент и люди совместно готовят и проверяют изменение | COL-1; workspace/AST/check; сеанс COL-2 для live-сценария |
| MOB-1 | Единый мобильный Shell для iOS/Android, операторов, инженеров и бизнеса | COL-1; AGT-1 для разработки; Presentation/replay для соответствующих видов |
| FIELD-1 | Голосовая работа при монтаже и пусконаладке | COL-2, AGT-1, MOB-1; реальная диагностика runtime |
| EVID-1 | Документы и наблюдения → проверяемый DSL draft | COL-1, AGT-1; importer boundaries |
| SPACE-1 | Площадки, здания, помещения, пространственный контекст | Общая топология/геометрия; COL-2 для присутствия |
| CCTV-1 | Существующие камеры/VMS в инженерном обсуждении | COL-1; camera source kit; SPACE-1 только для геометрии покрытия |

Базовый mobile web, domain-карточки и read-only интеграцию камеры можно делать параллельно
с коллаборацией. Для первого сценария достаточно ссылки на оборудование и изображения:
не нужно блокировать его на нативных сборках, голосе, документах или 3D-здании.
Незавершённые Presentation, replay, typed reports и runtime isolation из матрицы возможностей
остаются явными зависимостями, а не объявляются готовыми этим планом.

## COL-1 — участники, обсуждения и общий контекст

Владелец: общие контракты ресурсов и отображения в IDE; идентичность, членство,
долговременное хранение и доставка в Cloud/integration layer.

- [ ] Ввести идентичность участника Saturn с привязками к провайдерам входа. Приглашать
  инженера, оператора, монтажника и заказчика без обязательного доступа к GitHub-репозиторию.
  Существующие GitHub-права сохраняют независимое действие и не маскируются UI.
- [ ] Поддержать обсуждения проекта и задачи с несколькими участниками, упоминаниями,
  передачей задачи и явной областью доступа. Один разговор может ссылаться на несколько
  устройств; у одного устройства может быть несколько разговоров.
- [ ] Заменить историю одной вкладки долговременными сообщениями и событиями с server-assigned
  авторством, идентификаторами, временем, идемпотентным приёмом, восстановлением после reconnect
  и состоянием прочтения. Человек, запуск агента и результат действия различаются.
- [ ] Зафиксировать ссылку на ресурс вместе с контекстом отправки: project, environment,
  revision, entity/selection, view, момент истории и доступный снимок наблюдения.
  Переименование, удаление или последующее выделение не должны переадресовывать старое «здесь».
- [ ] Прикреплять оборудование, сигнал, участок чертежа, кадра, интервал видео/тренда,
  HMI, документ, alarm, отчёт и предложение изменения через общие ссылки. Отметка на фото
  остаётся отметкой, пока её соответствие оборудованию не установлено.
- [ ] Проверять права на сообщения, вложения, связанные ресурсы и подписки на сервере,
  включая отзыв доступа. Приглашение в thread не открывает весь проект. Агент не пересказывает
  общему кругу сведения, доступные только одному участнику; публикация вовне явная.
- [ ] Построить Inbox и доставку упоминаний/alarms/отчётов из сохранённых событий: очередь,
  повторы с дедупликацией, настройки адресатов и deep links. Доставка не требует запуска LLM;
  недоставленный push не считается подтверждением alarm или гарантированным оповещением.

**Приёмка:** два разных пользователя открывают одно обсуждение на разных устройствах;
после закрытия клиента и переподключения видны те же сообщения и исторические ссылки.
Повтор запроса не создаёт вторую запись. Отозванный участник теряет чтение и подписку.
Обсуждение неисправности, её alarm и исправляющее изменение не закрывают друг друга автоматически.

## COL-2 — совместные сеансы, присутствие и дисплеи

Владелец: контракты и поверхности Shell; организация сеансов и transport adapters в Cloud/host.

- [ ] Открывать совместный Session поверх долговременного обсуждения. Один участник может
  присутствовать с телефона и компьютера; устройства не дублируют его идентичность.
- [ ] Показывать текущий ресурс, выделение, курсор и 2D/3D-ракурс участника или агента.
  Присутствие, направление взгляда и preview жеста имеют временный срок жизни, не пишутся в Git.
- [ ] Дать действия «Показать мой вид», «Следовать за участником», «Перейти к выделению».
  У каждого остаётся собственная поверхность; follow включается добровольно и сразу отключается.
- [ ] Зарегистрировать и явно связать дисплей/рабочее место с проектом и средой, в том числе
  через pairing/QR. Общий монитор — адресат отображения, а не участник или источник полномочий.
- [ ] Реализовать «выведи это на тот монитор»: разрешённый view intent с конкретными
  ресурсом, environment и revision; отчёт об открытии или отказе. Для личного экрана другого
  человека отправляется приглашение, а не принудительное переключение.
- [ ] Разделить виртуальную точку обзора, физическую камеру, цифровой захват дисплея эмулятора
  и сохранённый кадр. Для агента явно показывать источник, выбранный вид и свежесть изображения.
  Квитанция открытия HMI и наблюдение изображения — разные результаты.
- [ ] Подключать голос/видеосвязь отдельным транспортом с явным участием. Текст, права,
  проектные операции и восстановление обсуждения продолжают работать без медиа.

**Приёмка:** монтажник выделяет AI3 на телефоне, инженер переходит к тому же входу в IDE,
агент получает ту же разрешённую ссылку; диагностика открывается на выбранном мониторе.
Движение камеры одного участника не перехватывает чужой экран без follow. Разрыв сеанса
не теряет обсуждение и не оставляет фантомного присутствия.

## AGT-1 — совместная разработка с Saturn Agent

Владелец: workspace/core operations в IDE; выполнение агента, модель и внешние интеграции в Cloud.

- [ ] Представить агента участником с конкретным запуском, инициатором, задачей,
  ограниченными полномочиями и сроком делегирования. Вызывать упоминанием или назначением;
  не отвечать на каждую реплику группы автоматически.
- [ ] Показывать ход задачи, использованные источники, результаты tools, ошибки, обоснования
  и неизвестные параметры. Дать возможность уточнить, остановить и передать задачу человеку.
- [ ] Расширять общие типизированные операции проекта для создания/изменения оборудования,
  соединений, привязок сигналов, HMI и отчётов. Агент и визуальный редактор используют один
  workspace/AST путь, сохраняющий исходник; отдельный AI DSL или equipment graph запрещён.
- [ ] Сделать изменение единицей совместной работы: base revision, инженерный diff,
  интерактивный preview, затронутые зависимости, исходники, проверки, замечания и evidence.
  Человек редактирует предложение и повторяет проверки вместе с агентом.
- [ ] На принятии проверять исходную версию/CAS; изменившиеся основания дают конфликт
  и повторную проверку, а не скрытую перезапись. Draft не меняет applied runtime.
- [ ] Синхронизировать визуальные жесты как временный preview с одной итоговой операцией
  и undo. Совместное текстовое редактирование/CRDT подключать к тому же source-документу
  только по необходимости; не превращать его в независимую модель оборудования.
- [ ] Рендерить в сообщениях те же Saturn Elements, что в обычном UI: Equipment, Signal,
  Trend, Alarm, Command, Revision, Deployment, Report, HMI, Incident и Person.
  Интерактивные ответы собираются из разрешённых компонентов и данных, не произвольного
  сгенерированного исполняемого UI. AI Elements — UI-основа; AI/Chat SDK — адаптеры,
  не владельцы инженерной истории, прав или runtime.
- [ ] Разделить предложение, успешный check, review, commit, publish и apply. Подтверждение
  команды контроллером и наблюдение достигнутого состояния показывать отдельно.
  Неопределённость/timeout не отображать как успех; переподключение не повторяет live-команду.

**Приёмка:** инженер просит добавить резервный насос в тестовую модель, уточняет положение
пальцем, исправляет HMI и запускает сценарий отказа. Агент показывает настоящий diff и результаты.
Одновременная правка коллеги вызывает обнаруживаемый конфликт. До разрешённого apply рабочий
объект не меняется. Никакой служебный токен не появляется в контексте модели или сообщениях.

## MOB-1 — Saturn Mobile для iOS и Android

Владелец: переиспользуемые Shell/domain surfaces в IDE; мобильный host, авторизация,
уведомления и Cloud-композиция вне доменного ядра.

- [ ] Создать один мобильный Shell с разной глубиной работы по capabilities, а не три
  отдельные модели или приложения. Начальный UX-кандидат: Today / Object / Agent / Inbox;
  навигация уточняется реальными сценариями, project/environment видны постоянно.
- [ ] Сохранить полноценное авторство с телефона: разговор → живая сцена/экран → выбор
  элемента → изменение → симуляция/check → review. Исходники и diff доступны по необходимости;
  разработка не сводится к запуску заранее подготовленных desktop-команд.
- [ ] Использовать общий React/domain UI и AI Elements как исходное направление. Проверить
  Capacitor как вариант iOS/Android host, общий web/PWA и необходимые native adapters.
  Не выдавать web-компоненты за готовые Swift/Kotlin primitives или браузерный тест за тест приложения.
- [ ] Реализовать уведомления и переход прямо к incident/thread/equipment. Проверить foreground,
  background, закрытый клиент, отозванный доступ, смену проекта и повторную доставку на iOS/Android.
- [ ] Сохранять локальный draft и показывать offline/stale/неполные данные. После reconnect
  догружать историю и проверять версии; физические команды не ставить в offline-очередь.
- [ ] Предоставить инженеру read-only просмотр рабочего места оператора: та же canonical
  Presentation, выбранный viewport и конкретная applied revision. Preview роли не является
  входом от имени оператора и не расширяет текущие права. Различать live, draft и симуляцию.
- [ ] Добавить «что видел оператор в момент события»: retained Presentation/revision,
  recorded telemetry, команды и ответы, связанные наблюдения. Replay изолирован от управления;
  пробелы данных и невозможность точного восстановления показаны явно. Это не VNC и не обещание
  точной копии экрана без сохранённого состояния сеанса.

| Рабочее пространство | Основные экраны и действия |
| --- | --- |
| Оператор | Смена, handover, alarms, HMI, оборудование, тренды, допустимые controls, lifecycle команд, связь с инженером и Agent |
| Инженер | Incidents, topology/подключения, raw I/O, quality/timestamps, source/used-by, диагностика протокола, revisions, проверки, deployment и проектирование |
| Бизнес | Площадки, доступность, простой, выпуск/энергия/расходы/SLA при наличии данных, отчёты, существенные incidents, обсуждения и разрешённые approvals |

KPI имеют определения, источники, период, часовой пояс и coverage. Agent не придумывает
причины простоя или финансовые результаты при отсутствии соответствующих наблюдений.
Состав UI определяется правами и задачей; скрытая кнопка не является проверкой доступа.

**Приёмка:** оператор открывает push и видит alarm/оборудование; инженер входит в то же
обсуждение, диагностирует сигнал, предлагает изменение и просматривает операторский экран;
руководитель видит разрешённый отчёт по тому же событию. Проверяются реальные iOS/Android
сборки, touch-UX, темы, узкий viewport и восстановление после потери связи.

## FIELD-1 — монтаж и пусконаладка на месте

Владелец: общий контекст/операции Shell и workspace; voice/discovery/display adapters в host/integration.

- [ ] Поддержать голосовые задачи «я подключил PLC в ШУ-2», «этот вход — давление перед
  насосом», «выведи входы на этот монитор». Речь использует те же ссылки и операции, что текст.
- [ ] Разрешать «этот», «сюда» и «тот» по выбранному ресурсу, сеансу, pairing, QR/NFC или
  явному выбору. При неоднозначности показывать кандидатов, не угадывать physical target.
- [ ] Сопоставлять доступное через разрешённый шлюз оборудование с ожидаемой конфигурацией.
  Заявление о монтаже, обнаружение устройства, ответ протокола, изменение входа и проверка
  соответствия физическому датчику сохраняются как разные результаты.
- [ ] Показывать raw и преобразованное значение, единицы, качество, источник и время.
  Недостающие диапазоны, распиновка и параметры датчика требуют решения; не заполнять их догадкой.
- [ ] Вести проверку подключения с фото/видео/телеметрией, замечаниями и handoff другому
  участнику. Сравнивать проектное, заявленное и проверенное фактическое состояние.
- [ ] Открывать на выбранном дисплее диагностику, HMI, тренд или дисплей эмулятора, возвращая
  результат операции. Управление оборудованием остаётся отдельной разрешённой командой;
  монтажное наблюдение или фраза в чате не разрешают запись в выходы.

**Приёмка:** у шкафа инженер связывает PLC с проектом, открывает входы на мониторе,
подключает датчик и проверяет наблюдаемое значение. Коллега видит контекст удалённо.
Saturn явно отмечает, что ещё не проверено, включая физическое соответствие датчика.

## EVID-1 — проектирование из чертежей и документов

Владелец: общий proposal/evidence contract; парсеры в project-owned importer/source kits;
доступ к материалам и выполнение агента в integration layer.

- [ ] Принимать схемы/P&ID, планы, PDF, схемы шкафов, I/O-таблицы, паспорта, фотографии,
  видео обхода и пояснения участников. Для каждого формата показывать фактически прочитанные
  части и неподдержанные данные; «любые документы» не означает молчаливое угадывание содержимого.
- [ ] Извлекать кандидатов оборудования, портов, связей, сигналов, HMI и правил, затем
  предлагать обычный authored TS draft через importer/workspace boundary. Не исполнять
  вложения/сгенерированный код в OAuth-сервисе и не менять applied при импорте.
- [ ] Для решения сохранять основания: версия/hash документа, страница и область,
  лист/строка/ячейка таблицы, источник и интервал видео, кадр, автор и время наблюдения,
  environment, revision и использованное преобразование. Утверждение и его подтверждения
  ссылаются друг на друга, а не помещаются неструктурированным текстом в комментарий.
- [ ] Отмечать assumptions, противоречия, нераспознанные элементы и требуемые решения.
  Оценка уверенности не выдаётся за калиброванную вероятность или инженерную проверку.
  Топологическая схема без масштаба не становится точной геометрией помещения.
- [ ] Дать сравнение документ ↔ DSL ↔ runtime/наблюдение, действие «покажи основание»
  и переход от элемента сцены к первоисточнику. Обновление документа или изменившийся контекст
  помечают зависимые решения для повторной проверки, не переписывают историю.
- [ ] Подкреплять предложение настоящими screenshot/video из Saturn, эмулятора,
  камеры или разрешённой записи плюс результатами теста. Render доказывает render,
  эмулятор — поведение эмулятора; ни один не подменяет доказательство физической установки.
- [ ] Сохранять загруженный материал отдельно от созданного результата и проверенного evidence.
  Ограничить доступ и сроки хранения; передача изображений внешней модели — отдельное разрешение.
  Содержимое документа не является инструкцией на получение новых полномочий агентом.

**Приёмка:** по чертежу, I/O-list и фотографии создаётся проверяемый TS draft со сценой,
сигналами и HMI. Каждый значимый вывод имеет источник или явное допущение. Намеренно внесённое
противоречие остаётся видимым. Человек исправляет предложение, а реальная запись проверки
показывает результат и его ограничения; неподдержанные части не исчезают из отчёта.

## SPACE-1 — здания, помещения и пространственная коммуникация

Владелец: общие пространственные отношения в модели, проекции Shell; импорт геометрии в source kits.

- [ ] Описывать площадку, здание, этаж, помещение/зону, границы и локальные координаты.
  Разделить «находится в», «подключён к», «управляет» и «наблюдает»: камера может стоять
  в одном помещении и смотреть в другое, контроллер — управлять удалённым оборудованием.
- [ ] Начать с плана этажа с заданным масштабом, помещений и расстановки оборудования.
  Расширять до высот монтажа, 3D-геометрии, препятствий и точек крепления без второго source.
- [ ] Предусмотреть явный импорт планов/BIM/IFC через адаптер с сохранением ссылок на
  исходные элементы и ограничений импорта; не строить обязательный полный BIM/CAD-редактор.
- [ ] Показывать участников и агента как виртуальные точки обзора с направлением взгляда,
  frustum, выделением и возможностью follow. Сохранённый view — проектный ресурс;
  текущий «полёт» камеры — состояние сеанса.
- [ ] Показывать связь вида с оборудованием, экраном/монитором и изображением, которое
  участник или агент рассматривает. Если у физического снимка нет установленной pose,
  не рисовать выдуманное точное положение камеры в модели.
- [ ] Обобщить физическую камеру как project-owned equipment через общий device contract:
  положение, крепление, питание/порты/кабель/коммутатор, диагностика и media capabilities.
  Поток — медиавозможность, доступность — сигнал, детекция — событие; несколько потоков
  одного устройства не создают несколько независимых единиц оборудования.

**Приёмка:** на плане насосной видны насос, PLC, дисплей и камера с инженерными связями.
Участники независимо рассматривают объект и могут перейти к виду коллеги. 2D/3D и DSL
согласованы. Виртуальный ракурс не изменяет pose оборудования и не отправляет PTZ-команды.

## CCTV-1 — интеграция существующих камер и видеорегистраторов

Владелец: project-owned camera/VMS adapters и Cloud/media integration; доменная идентичность
оборудования и ссылки на наблюдения остаются общими.

- [ ] Подключать доступные потоки, события и поиск/воспроизведение записей существующих
  камер, NVR/VMS через адаптеры с явным описанием фактических capabilities устройства.
  Протокольная и vendor-специфика не входит в core; начальный сценарий read-only.
- [ ] Оставить непрерывную запись и основной архив на существующей стороне. Media transport
  отделить от телеметрии и Git; не проксировать весь видеоархив через проектную историю.
- [ ] Связать alarm/incident/equipment/помещение с камерой и временем записи. Показать
  актуальность потока, качество и расхождение часов/отсутствие точной синхронизации;
  отсутствие изображения не скрывать успешно загруженной старой миниатюрой.
- [ ] Дать «открыть видео», «показать на мониторе», «приложить наблюдение» и «спросить Saturn»
  в том же обсуждении. Последнее требует отдельного разрешения передачи кадров модели.
- [ ] Ссылки на внешние записи учитывают срок хранения и исчезновение архива. Явно сохранять

  ссылка останется доступной навсегда. Секреты и временные media URLs не попадают в Git/LLM.
- [ ] Разделить просмотр live, архив, экспорт evidence, PTZ и администрирование.
  Физический поворот камеры не равен изменению её проектной pose или ракурса участника.
- [ ] После SPACE-1 поддержать предложение размещения камеры: масштаб, высота, оптика,

**Приёмка:** из alarm по насосу участник открывает связанную существующую камеру и доступную
запись рядом с трендом, отправляет вид на монитор и сохраняет разрешённое наблюдение в thread.
Тесты покрывают отказ/устаревший поток, недоступный архив, расхождение времени и запрет экспорта.

## Разделение ответственности и хранения

| Слой | Ответственность |
| --- | --- |
| IDE core / workspace | Канонические ресурсы и ссылки; обычный TS; AST/import/change operations, версии, check и проектные артефакты |
| IDE Shell / host | Общие domain-компоненты, поверхности, selection/view intents, присутствие, mobile/local composition и adapters |
| Runtime | Наблюдения, quality/time, команды, alarms, история и applied authority; работа не зависит от открытого чата |
| Cloud / saturn-saas | Identity, членство, обсуждения, durable storage, доставка/уведомления, sessions, выполнение агента и инфраструктурные adapters |
| saturn-plugins / project source kits | Камеры/протоколы, внешние форматы документов и геометрии, device/target implementations без global registry |
| saturn-examples | Воспроизводимые проекты и сквозные сценарии с фактическими результатами проверок |

IDE не импортирует SaaS, GitHub OAuth, AI Gateway, конкретную VMS или библиотеку доставки
как доменную зависимость. Без подключённого AI и Cloud локальные проект и runtime сохраняют
свои возможности. Контракты коллаборации не вводят второй runtime authority.

| Данные | Хранение / срок жизни |
| --- | --- |
| Authored модель, исходники, сохранённые виды | Проект / Git |
| Обсуждения, сообщения, предложения, ссылки и квитанции | Долговременное хранилище коллаборации; ссылки на authoritative runtime events |
| Присутствие, курсоры, ракурсы, preview жестов | Временное состояние сеанса с истечением |
| Telemetry, команды и история исполнения | Runtime/history с собственным provenance |
| Непрерывное видео и основной архив | Существующие камеры / NVR / VMS |
| Загруженные документы и явно сохранённые evidence clips | Отдельное защищённое хранилище с доступом/retention; в проекте ссылки и версии |

Chat SDK рассматривается как интеграционный адаптер каналов, AI SDK — адаптер модели,
AI Elements — UI primitives. Их служебные user/assistant/tool roles и state не заменяют
идентичность участников, историю Saturn или проверку capabilities. Конкретный media transport,
мобильный host и механизм совместного текста выбираются при реализации соответствующего
сценария; roadmap не фиксирует неподтверждённую совместимость библиотек.

## Первый сквозной результат и дальнейшая демонстрация

**Первый вертикальный срез:** монтажник на мобильном web выделяет вход PLC в обсуждении;
инженер открывает эту же ссылку в браузере; Agent объясняет доступное наблюдение и предлагает
проверяемое изменение. Диагностика показывается на зарегистрированном мониторе. К обсуждению
прикладывается разрешённое наблюдение существующей камеры/эмулятора с честным указанием источника.
На следующий день контекст, участники, решение, проверки и реальное состояние изменения
восстанавливаются из сохранённых данных.

**Расширение демонстрации:** чертёж + I/O-list + фото → DSL draft → настоящие 2D/3D и HMI →
голосовое уточнение при монтаже → проверка сигнала → согласованное изменение → отдельный
разрешённый apply → alarm → push оператору → совместная диагностика/replay → бизнес-отчёт
по тому же событию. Для каждого перехода показываются среда, версия, источники и ограничения.

Демонстрация и познавательная документация используют настоящие компоненты Saturn,
рендеры и результаты. Сгенерированная картинка, мок ответа или наличие тестового файла
не являются доказательством работы продукта.

## Правила закрытия этапов

У каждого закрытого пункта должны быть commit/implementation reference, воспроизводимый
сценарий, фактически выполненные проверки с указанным host/runtime и результатом, а для
визуального/мобильного поведения — реальные кадры/видео и оценка UX. Не запускать формальную
галочку только потому, что код скомпилировался.

Проверять не только happy path: конфликт правок, отзыв прав, недоступный источник,
устаревшее значение, разрыв связи, повторную доставку, неверную среду/revision, ошибку агента,
неполный replay и независимость runtime от отказа Cloud/чата. Изменение без источника или
неподтверждённый physical outcome остаются явно непроверенными.

## Что намеренно не входит в ближайший объём

Собственный NVR и непрерывный видеоархив; обязательный полный BIM/CAD; VNC как основа
просмотра операторского HMI; обязательный CRDT или распределённый event-sourcing для всей
системы; дублирующая инженерная модель внутри чата; скрытая выдача прав агенту; автоматическое
применение по голосовой реплике; выдача уверенности модели/кадра эмулятора за факт физической
проверки. Эти ограничения не сокращают существующие обязательства матрицы возможностей.
