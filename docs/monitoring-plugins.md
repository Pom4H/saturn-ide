# Project-owned monitoring rules

Monitoring rules are ordinary TypeScript source in the engineering project. A copied
plugin exports declarations; `project.ts` imports them explicitly. The declaration
becomes part of the checked `saturn.build@2` model, so changing a limit changes the
artifact identity. The Performance surface receives the applied project from runtime
and reads the current `Snapshot`; saving or checking a source file alone does not
activate a new rule.

```ts
// plugins/pump-monitor.ts
import { monitor, monitorMetric, signal } from '@saturn/core';

export const pressure = signal('pump.pressure', {
  initial: 0, unit: 'bar', staleAfter: 10_000,
});

export const pumpHealth = monitor('pump-health', {
  label: { en: 'Pump health', ru: 'Состояние насоса' },
  metrics: [monitorMetric('pressure', pressure, {
    warning: { below: 2, above: 6 },
    critical: { below: 1, above: 9 },
    maxAgeMs: 3_000,
  })],
});

// project.ts
import { project } from '@saturn/core';
import { pumpHealth } from './plugins/pump-monitor';

export default project({
  id: 'pump-project', label: 'Pump project',
  equipment: [], pipes: [], alarms: [], monitoring: [pumpHealth],
});
```

The metric references the canonical numeric `Signal`, which `project()` includes in
its derived signal index. A device-owned signal can be used the same way. Conditions
are data, not callbacks: runtime and browser can evaluate the same checked rule
without loading the plugin's authoring module again. There is no folder scan,
global registration or plugin activation lifecycle.

`evaluateMonitoring(project, snapshot, {now, connected})` from
`@saturn/core/monitoring` returns one read-only state per group and metric.
Thresholds use strict comparisons (`value > above`, `value < below`). Critical
limits take precedence over warning limits. Each metric can additionally demand
a fresher reading than its Signal's `staleAfter` with `maxAgeMs`. Group status is
critical if any metric is critical, then warning, then unknown, otherwise ok;
coverage counts actual usable readings out of declared metrics. An unavailable
metric does not hide a critical sibling.

Missing, stale, bad, offline, disconnected, expired or invalid readings produce
`unknown` with `value: null`. `signal.initial` is never presented as a live value.
An individual failed channel projection is contained so other groups still render.
No chart points or history samples are generated by monitoring rules.

These limits are **read-only visual health conditions**. They do not create an
`Alarm`, acknowledge one, issue commands or change acquisition/archive policy.
Author an `alarm()` separately when an operational alarm and its event history
are required. Runtime driver and historian remain the owners of observations.
The current contract handles numeric signals and per-signal limits/freshness;
it does not claim general derived-expression or arbitrary plugin-code parity.
