# Требования к обмену и архиву сигнала

У сигнала одна авторская декларация в TypeScript. `exchange` задаёт частоту **запросов конкретного канала** у способного на выборочное чтение протокола. `storage` выбирает, какие **уже принятые** наблюдения попадут в SQL-архив и на какой срок. Оба поля попадают в checked build и semantic diff. Они не заменяют качество, timestamp, provenance или состояние runtime.

```ts
import { signal } from '@saturn/core';
import { modbusTcp } from './plugins/modbus'; // исходник скопирован в проект

const line = modbusTcp('line', { host: '192.0.2.10' }, { pollMs: 100 });

// Для обучения: каждый принятый отсчёт, 30 дней. Дальнейший ML export — отдельная задача.
export const vibration = line.bind(signal('motor.vibration', {
  initial: 0, unit: 'mm/s', staleAfter: 1_000,
  exchange: { pollMs: 100 },
  storage: { mode: 'all', retentionMs: 30 * 86_400_000 },
}), { unit: 1, area: 'input', offset: 100, format: 'float32' });

// Для обычного наблюдения: реже запросы, меньше одинаковых строк архива.
export const temperature = line.bind(signal('motor.temperature', {
  initial: 0, unit: '°C', staleAfter: 10_000,
  exchange: { pollMs: 2_000 },
  storage: { mode: 'on-change', deadband: 0.2,
    maxIntervalMs: 5_000, retentionMs: 7 * 86_400_000 },
}), { unit: 1, area: 'input', offset: 120, format: 'float32' });
```

`source.options.pollMs` — минимальный поддерживаемый интервал источника. `exchange.pollMs` должен быть целым числом от `source.options.pollMs` до 24 часов. Планировщик использует monotonic clock, не `sourceAt`; запросы одного подключения последовательны и не перекрываются. Только плагин с `defineProtocol({ perSignalPolling: true, … })` может исполнить это требование. Его `read(channels)` должен читать **ровно переданные** каналы. Неподдерживающий плагин или pinned legacy wrapper получают `PROTOCOL_POLL_POLICY` до открытия соединения. У MQTT частоту задаёт издатель; JSON/HTTP в текущем виде получает весь ответ GET, поэтому эти плагины не объявляют выборочный опрос. Изменение частоты требует Checked → Published → Applied для live runtime.

Без `storage` каждый принятый отсчёт архивируется на 7 дней, как раньше. `on-change` пропускает повторяющиеся значения в SQL-архиве: числовой отсчёт записывается, если разница с последним **архивным** значением строго больше `deadband`; `maxIntervalMs` записывает очередной пришедший отсчёт после заданного интервала. Он **не создаёт** измерение, если источник молчит. Первый отсчёт, смена качества, новый telemetry run, выход/возврат тревоги и восстановление наблюдений после stale записываются независимо от deadband. Live snapshot и тревоги видят все принятые данные; команды эта политика не меняет.

`retentionMs` — целое число от 1 часа до 365 дней. Для каждой строки при записи сохраняется `expires_at`; изменение проекта влияет на новые строки и не сокращает задним числом срок уже записанных. У старых строк без `expires_at` остаётся прежний срок 7 дней. SQLite и PostgreSQL используют тот же контракт, но проверка per-signal migration и restart пока выполнена на SQLite; PostgreSQL интеграционный тест запускается при `TEST_POSTGRES_URL`.

Редкий архив снижает полноту исторических отчётов: интервалы без записанных данных остаются `null` или имеют частичное coverage. Ни `on-change`, ни график не восстанавливают отброшенные отсчёты. Для обучения и анализа быстрых переходных процессов нужен `mode: 'all'` и достаточная частота источника. Это сохраняет все **принятые** наблюдения, но не обещает точность датчика между ними. Исторический UI строит максимум 1200 SQL-корзин на запрос. Обычный отчёт ограничен 50 000 архивных строк на сигнал за выбранный период (100 ms — примерно 83 минуты непрерывных отсчётов); длинный ML отчёт и потоковый raw export ещё не созданы.

При непрерывном интервале 100 ms за 30 дней получится около **25,9 млн принятых отсчётов на один канал** до пропусков. Объём SQLite/PostgreSQL, I/O и резервные копии надо рассчитывать отдельно; UI пока не оценивает ёмкость. Фактический опрос может идти медленнее заданного интервала из-за времени ответа и backpressure.
