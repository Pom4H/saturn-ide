# DSL и TypeScript в Saturn IDE

DSL Saturn — предметный язык описания инженерного объекта, встроенный в обычный TypeScript. Его словарь задаёт библиотека `@saturn/core`: оборудование, сигналы, физические соединения, тревоги, HMI и отчёты. Нового синтаксиса или отдельного языка скриптов здесь нет.

**TypeScript даёт средства выразить и проверить связи. Saturn определяет, что эти связи означают для инженерного объекта.**

## Одна модель объекта

```text
project.ts + обычные imports
             │
       проверки TypeScript
             │
       исполнение деклараций
             │
       валидация модели Saturn
             │
       проверенный BuildArtifact
             │
   publish → apply → runtime
                         │
                показания и качество
                         │
              HMI / тревоги / история
```

Схема, HMI, перечень сигналов и документация объекта используют эту модель. Наблюдения оборудования и история принадлежат runtime. Исходник, проверенная сборка, опубликованная и применённая ревизии — разные состояния.

«Одна модель» не означает «весь проект в одном файле». `project.ts` собирает объект из модулей. Исходники могут лежать в `equipment/`, `reports/`, `plugins/` и других обычных каталогах. Производные индексы и артефакты не нужно редактировать как ещё одну базу тегов.

## Первый проект

Авторские названия и описания — обычные строки: `label: 'Насос'`,
`description: 'Подача воды'`, `column(flow, 'mean', 'Расход')`. Перевод на два языка
не входит в контракт DSL. Язык интерфейса IDE и системных диагностик выбирается
отдельно и не меняет авторский текст. Старые `{ru, en}` читаются для совместимости;
новые объявления, scaffold и предложения правок не требуют `locale` или словаря
переводов. Название и краткое описание project-owned импортёра также могут быть строками.

Этот `project.ts` описывает резервуар, насос и базовый ПЛК. Труба связывает водяные порты, кабель — дискретный выход ПЛК с входом пуска насоса. Тревога, отчёт и HMI ссылаются на те же экземпляры и сигналы.

```ts
import {
  alarm, autoHmi, cable, column, pipe, plc,
  project, pump, report, signal, tank,
} from '@saturn/core';

export const reservoir = tank('T-01', {
  label: 'Резервуар', x: 40, y: 80,
  level: signal({ initial: 0, unit: '%', staleAfter: 5000 }),
});

export const feed = pump('P-01', {
  label: 'Подающий насос', x: 300, y: 240,
  rpm: signal({ initial: 0, unit: 'rpm', staleAfter: 5000 }),
  run: signal({ initial: false, writable: true }),
});

export const controller = plc('PLC-01', {
  label: 'Контроллер', x: 560, y: 80,
});

export const flow = signal('feed.flow', {
  initial: 0, unit: 'm³/h', staleAfter: 5000,
});

export const hourly = report('hourly', {
  label: 'Работа насоса по часам',
  bucketMs: 3_600_000,
  columns: {
    speed: column(feed.rpm, 'mean', 'Средние обороты'),
    startCommand: column(feed.run, 'last', 'Последняя команда пуска'),
  },
});

export default project({
  id: 'pumping-station',
  label: 'Насосная станция',
  equipment: [reservoir, feed, controller],
  pipes: [pipe('suction', {
    from: reservoir.ports.outlet,
    to: feed.ports.inlet,
    flow,
  })],
  cables: [cable('start-cable', {
    from: controller.ports.DO1,
    to: feed.ports.run,
    signal: feed.run,
  })],
  alarms: [alarm('high-speed', {
    label: 'Высокие обороты', signal: feed.rpm,
    above: 2900, hysteresis: 100,
  })],
  reports: [hourly],
  hmi: autoHmi(controller),
});
```

Это описание модели, **не готовое подключение к физическому ПЛК**. В примере нет драйвера или симулятора в `server.ts`; показания от оборудования сами не появятся. `initial: 0` задаёт исходное значение в декларации и помогает вывести тип, но не доказывает, что насос остановлен или резервуар пуст. Команда `run` тоже не является подтверждением вращения: для обратной связи нужен измеренный сигнал.

Внутри `pump(...)` вызов `signal({ ... })` создаёт спецификацию сигнала без ручного ID. Экземпляр материализует `feed.rpm` с ID `P-01.rpm` и владельцем `P-01`. `signal('feed.flow', ...)` создаёт отдельный проектный сигнал с явным ID. `project(...)` собирает индекс сигналов из оборудования и потребителей, поэтому перечислять все сигналы повторно не требуется.

`const feed` — имя переменной TypeScript; `'P-01'` — ID оборудования; `label` — подпись для человека. Это разные вещи. `feed.ports.outlet` — физический порт, а `feed.rpm` — сигнал, не его текущее числовое значение. `export default` задаёт модель, которую загружает сборщик Saturn.

## Словарь DSL

Пустой проект с текущим core не требует списков:

```ts
import { project } from '@saturn/core';
export default project({ id: 'empty', label: 'Новый объект' });
```

При добавлении оборудования индекс сигналов выводится из его полей:

```ts
import { command, project, pump } from '@saturn/core';
const feed = pump('P-01', { label: 'Насос', x: 100, y: 100 });
const station = project({ id: 'station', label: 'Станция', equipment: [feed] });
const speedId: 'P-01.rpm' = station.signals['P-01.rpm'].id;
const start = command(station.signals['P-01.run'], true);
```

Здесь команда только создаётся как типизированное значение, не отправляется в runtime.
Проверенная модель содержит массивы `equipment`, `pipes`, `alarms` и канонический
индекс сигналов. Для условных объявлений и коллекций, чей состав неизвестен при
проверке типов, доступ к сигналу требует проверки наличия.

Существующий standalone starter пока закреплён на более ранней Git-ревизии core,
поэтому scaffold сохраняет совместимые явные пустые списки. Чтобы использовать
новые defaults вне текущего IDE checkout, dependency проекта должна указывать на
версию core с этой реализацией; старый pin автоматически не обновляется.

| Примитив | Инженерный смысл | Важная граница |
|---|---|---|
| `device()` | Определение класса: порты, сигналы, знания, возможности, шаблоны тревог | Возвращает конструктор экземпляров; глобальный реестр плагинов не нужен |
| `pump()`, `tank()`, `valve()`, `plc()` | Встроенные классы оборудования | Используют тот же `device()`, что и проектные классы |
| `tee()` | Тройник трубопровода с тремя passive fluid-портами `left/right/branch` | Это явный узел топологии; простое пересечение трасс соединением не является |
| `signal()` | Объявление измеряемой или управляемой величины | Декларация не равна наблюдению |
| `terminal()` | Физический порт: среда, семейство, направление, геометрия | Свойства порта принадлежат классу оборудования |
| `enclosure()`, `mount()` | Шкаф/корпус и физическое положение оборудования внутри него | Монтажные координаты независимы от x/y технологической схемы |
| `pipe()` | Труба с жидкостью и ссылкой на расход | Не конвейер вычислений и не зависимость сигналов |
| `cable()` | Соединение управления, питания или шины | Кабель не создаёт сетевой драйвер |
| `bind()`, `protocol.*()` | Привязка сигнала к адресу источника | Описание адреса не открывает соединение |
| `command()` | Типизированное описание записи в writable-сигнал | Возвращает данные команды; само по себе ничего не отправляет |
| `alarm()` | Верхний порог числового сигнала с гистерезисом | Состояние и квитирование принадлежат runtime |
| `column()`, `report()` | План агрегации истории по ссылкам на сигналы | Пропуски данных не превращаются в нули |
| `hmi()`, `autoHmi()` | Именованный интерфейс или представление по топологии | Это не прошивка физического экрана |
| `project()` | Сборка и проверка единой модели | Не запускает сбор сигналов и не применяет ревизию |

### Физический монтаж и 2-way edit

Монтаж — ещё одна проекция той же модели, а не отдельный файл раскладки. Класс оборудования объявляет реальный footprint в миллиметрах, экземпляр хранит независимую позицию внутри шкафа:

```ts
import { device, enclosure, mount, project } from '@saturn/core';

const plcClass = device({
  id: 'saturn-plc',
  icon: 'plc',
  ports: {},
  capabilities: { mounting: { width: 108, height: 90, depth: 62 } },
});
const cabinet = enclosure('CAB-1', {
  label: 'Шкаф автоматики', width: 800, height: 600, depth: 250, grid: 5,
});
const controller = plcClass('PLC-01', {
  label: 'Контроллер',
  x: 560, y: 80,
  mount: mount(cabinet, { x: 40, y: 60 }),
});

export default project({
  id: 'cabinet-demo', label: 'Cabinet demo',
  enclosures: [cabinet], equipment: [controller], pipes: [],
});
```

Перетаскивание в представлении «Монтаж» меняет только числовые литералы `mount.x/y` в TypeScript. Валидатор тем же кодом проверяет границы шкафа, глубину и пересечения оборудования; неверная позиция не становится отдельным UI-состоянием и не попадает в BuildArtifact.

`autoHmi(controller)` выбирает достижимое по физическим связям оборудование и исключает сам контроллер. Это проекция связности, а не автоматически спроектированный технологический процесс. `PresentationElement` позволяет описывать элементы экрана, которые не являются физическим оборудованием; они тоже используют канонические сигналы.

## Что даёт TypeScript

### Имена и типы выводятся из объявления

Из `initial: 0` получается числовой сигнал, из `initial: false` — логический. Generic-параметры `Signal<T, ID, W>` сохраняют тип значения, ID и возможность записи. Обычно писать эти параметры руками не требуется: функции DSL выводят их из аргументов.

В следующем самостоятельном примере строки с `@ts-expect-error` намеренно неправильные. Директива нужна тесту документации: если запрещённая операция вдруг начнёт приниматься, проверка упадёт. В рабочем проекте не следует подавлять такие ошибки.

```ts
import { column, command, pump, type SignalValue } from '@saturn/core';

const p = pump('P-01', { label: 'Насос', x: 100, y: 100 });
const rpmId: 'P-01.rpm' = p.rpm.id;
const speed: SignalValue<typeof p.rpm> = 1450;

// Только проверка типов; эту функцию не вызываем.
function checkTypes() {
  command(p.run, false);
  column(p.rpm, 'mean', 'Средние обороты');

  // @ts-expect-error Логическая команда не принимает строку.
  command(p.run, 'off');
  // @ts-expect-error Измеренный rpm не объявлен writable.
  command(p.rpm, speed);
  // @ts-expect-error Среднее арифметическое требует числа.
  column(p.run, 'mean', 'Средняя команда');
  // @ts-expect-error У этого класса нет такого сигнала.
  p.pressure;
}
```

Так же типы портов ограничивают среду, семейство и направление соединения. В `pipe()` нельзя передать дискретный выход ПЛК вместо водяного выхода. Это работает, пока сохраняются конкретные выведенные типы; принудительные приведения типов способны обойти статические ограничения.

`SignalValue<typeof p.rpm>` получает тип значения из сигнала. `ReportRow<typeof hourly>` получает имена и типы колонок из определения отчёта, включая `null` для отсутствующего результата. Нет необходимости вручную поддерживать параллельные интерфейсы для тех же величин.

### Обычные модули и функции

Импорт сохраняет типы объекта. Повторяющиеся декларации можно вынести в функцию или файл; копирование строковых ID и отдельная схема регистрации для этого не нужны.

```ts
import { pump, signal, type SignalSpec } from '@saturn/core';

const stopped = {
  initial: false,
  writable: true,
} satisfies SignalSpec<boolean, true>;

export function standbyPump<const ID extends string>(id: ID, x: number) {
  return pump(id, {
    label: 'Резервный насос', x, y: 240,
    run: signal(stopped),
  });
}

export const reserve = standbyPump('P-02', 600);
const runId: 'P-02.run' = reserve.run.id;
```

`const ID` сохраняет конкретный ID в типе результата. `satisfies` проверяет соответствие контракту без замены результата проверки широким интерфейсом. `as const` полезен, когда нужно сохранить литералы в отдельном объекте конфигурации; ставить его на каждое объявление DSL не требуется.

Не расширяйте типы заранее до `Equipment` или `Record<string, Signal>`, если дальше нужны конкретные имена полей. Такие общие контракты полезны на границе универсального инструмента, но могут потерять точные подсказки экземпляра. Полная статическая точность автоматически собранного `project.signals` сейчас не равна точности `feed.rpm`: предпочтительнее сохранять прямые ссылки на владельцев.

### Подсказки и документация у кода

CodeMirror отображает код и диагностические диапазоны; TypeScript Language Service в workspace получает настоящие объявления, импорты и типы. Он даёт дополнение имён и hover-сигнатуры. `@ru` и `@en` в JSDoc выбираются по языку Shell. `Text` допускает обычную строку или объект `{ ru, en }` для пользовательских подписей.

Текст стандартных ошибок TypeScript сейчас передаётся одинаковым в поля `ru` и `en`; это не полноценный перевод диагностики TS. Доменные `ProjectError` имеют отдельные сообщения RU/EN. Подсказки не должны подменять реальные типы заранее составленным списком названий.

Переименование переменной средствами TypeScript и изменение инженерного ID — разные операции. Изменение `'P-01'` влияет на производные ID; `semanticId` позволяет явно закрепить семантическую идентичность. Для инженерного переименования нужны проверка зависимостей и просмотр diff, а не только поиск и замена текста.

## Что проверяется и когда

| Уровень | Что проверяет | Чего не доказывает |
|---|---|---|
| TypeScript | Известные поля, тип значения, writable-контракт, типы портов и агрегаций | Что контроллер существует, адрес верен или действие безопасно |
| Модель Saturn | ID, ссылки на те же объекты, занятость и совместимость портов, диапазоны деклараций, конфигурацию HMI и отчётов | Что физический монтаж соответствует модели |
| Runtime | Приём значений, качество, давность, команды, применённую ревизию и жизненный цикл драйвера | Универсальную отмену физического действия или аппаратную безопасность |
| Испытания объекта | Реальный обмен, монтаж, исполнительные механизмы и сценарии отказа | Не заменяются компиляцией проекта |

Типы TypeScript стираются при преобразовании в JavaScript. `as SomeType` не проверяет пакет от контроллера, а `readonly` не является универсальной заморозкой объекта во время исполнения. Поэтому на границах остаются проверки модели и входных данных.

Bun умеет выполнять и собирать TypeScript, но сам не выполняет проверку типов. В Saturn `Builder.build()` сначала вызывает `Language.diagnostics()`, затем `Bun.build()`, загружает декларацию и проверяет модель. Просто успешный запуск `bun project.ts` не равен успешному check в IDE.

## Сигнал и протокол

```ts
import { bind, protocol, signal } from '@saturn/core';

export const pressure = bind(
  signal('PT-01.pressure', {
    initial: 0,
    unit: 'bar',
    staleAfter: 5000,
  }),
  protocol.modbus('controller-01', 120, { pollMs: 1000 }),
);
```

`PT-01.pressure` — ID доменного сигнала. `controller-01` и `120` — описание источника и адреса, которое интерпретирует выбранный адаптер. Сам binding не задаёт IP-адрес, не гарантирует формат регистра и не запускает опрос. Смена адреса не требует переименовывать сигнал.

Фактический сбор выполняет импортированный драйвер. Публичный `defineProtocol()` описывает контракт адаптера; конкретная реализация и её SDK принадлежат проектному расширению. Протокол и физическая топология связаны инженерным смыслом, но `cable(...)` не превращается автоматически в TCP-соединение.

В примере `bind` применяется к явному сигналу до включения его в модель. Он возвращает новый объект с прежними типом и ID: нужно передавать потребителям именно эту ссылку. Нельзя независимо создавать несколько объектов с одним ID или заменить только одну из уже разошедшихся ссылок. Подробности: [сбор сигналов и протоколы](protocols.md).

## Собственный класс оборудования

```ts
import { device, signal } from '@saturn/core';

export const pressureTransmitter = device({
  id: 'pressure-transmitter',
  icon: 'signal',
  ports: {},
  signals: {
    pressure: signal({ initial: 0, unit: 'bar', staleAfter: 5000 }),
  },
  alarms: {
    high: { label: 'Высокое давление', signal: 'pressure', above: 6 },
  },
  knowledge: {
    summary: 'Датчик давления с верхним аварийным порогом.',
    commissioning: ['Проверить ноль и соответствие показаний эталону.'],
  },
});

export const pt = pressureTransmitter('PT-01', {
  label: 'Давление на выходе', x: 480, y: 160,
});
const pressureId: 'PT-01.pressure' = pt.pressure.id;
```

Файл класса можно хранить в `equipment/pressure-transmitter.ts` и импортировать обычным относительным импортом. Экземпляр владеет сигналом и тревогой; `project()` собирает их при включении `pt` в `equipment`. В этом учебном классе намеренно нет физических портов, собственного SVG, драйвера или аппаратной сертификации.

`terminal()` добавляет порты, `capabilities` описывает доступные представления и целевые возможности. Внешний вид и драйвер добавляются соответствующими проектными модулями. Каталог плагинов не сканируется ради скрытой активации: установка исходников и их явное подключение — разные действия.

## Визуальное редактирование и исходник

Перемещение оборудования изменяет авторские координаты через операции над TypeScript AST и диапазонами исходника. Во время жеста схема показывает preview, запись выполняется после завершения. TypeScript сам по себе не реализует two-way editing — это функция workspace и Shell Saturn.

Для непосредственного редактирования удобны распознаваемые объявления с числовыми литералами `x` и `y`, как в первом примере. Выражение, фабрика вроде `standbyPump(...)`, цикл или вычисляемое расположение могут быть корректным TypeScript и корректной моделью, но не иметь однозначного обратного преобразования в исходник. Корректность DSL не обещает визуальную редактируемость любого TS-кода. Изменяйте генератор в исходнике, когда редактор не может безопасно изменить декларацию.

Сохранение файла не применяет изменения к live-объекту. Preview доверенного симулятора в dev — отдельная возможность; `SATURN_PREVIEW=manual` отключает автоприменение preview. Проверенная сборка, publish и apply сохраняют отдельный жизненный цикл.

## Значение, качество и единицы

`Signal` хранит описание величины; `Sample` — наблюдение со значением, временем и качеством. `observation(snapshot, signal)` сохраняет тип значения и допускает отсутствие наблюдения. Для оценки давности используются правила runtime и операционные проекции, а не чтение `initial`.

Нельзя трактовать отсутствующие данные как ноль, устаревшие — как свежие, а команду пуска — как подтверждённое вращение. Отчёты сохраняют пропуски и покрытие данных. `mean`, `min`, `max` и `integral` предназначены для числовых сигналов; `last` поддерживает также логические и строковые значения. Интеграл расхода и сумма отсчётов расхода — разные операции; окна, временную базу и единицы результата нужно проверять в плане отчёта.

`unit` и `dimension` сейчас являются строковыми метаданными. У ряда физических соединений есть проверки совпадения единиц, но это не полная алгебра физических размерностей. Произвольные вычисляемые выражения, вывод единиц и полноценный runtime вычисляемых сигналов ещё не реализованы целиком. `origin.kind = 'derived'` описывает происхождение, а не создаёт вычислитель. Нельзя читать наличие поля в интерфейсе как обещание готовой функции.

## Граница исполнения

Импорт `project.ts` исполняет обычный код. Декларации должны быть предсказуемыми и без побочных эффектов: без сетевых запросов, записи в оборудование, секретов или зависимости идентичности от случайности и времени. I/O принадлежит драйверу, который запускается явным жизненным циклом. Проверка типов не является песочницей для недоверенных расширений.

Инженерный проект не становится программой жёсткого реального времени от того, что записан на TypeScript. Прошивка конкретного ПЛК, toolchain, память, пины и аппаратный HMI требуют отдельного target и испытаний. Контракт целевой сборки не доказывает поддержку произвольного TS на контроллере.

Для инженера и кодового агента правила одинаковы: использовать существующие определения, сохранять ссылки на владельцев и ID, проверять типы и модель, просматривать инженерный diff и явно применять проверенную ревизию. Отдельный DSL для ИИ не нужен.

## Проверка компактности остальных контрактов

- Сигналы экземпляра получают ID, владельца и семантическую identity автоматически.
  Не нужно повторять их в `project.signals`; `project()` собирает существующие ссылки.
  Явный registry остаётся для отдельных сигналов и совместимости. Прямое обращение
  к `equipment.field` и автоматически собранный индекс сохраняют точные ID, типы
  значений и writable для статически известных сигналов. Ключи индекса — реальные
  ID сигналов, а не имена полей входного `signals: {alias: signal}`. Динамические
  каналы/расширенные типы допускают неизвестный ключ только с проверкой наличия;
  TypeScript не обещает, что произвольный канал существует.
- `semanticId` необязателен для создания оборудования и изменения его подписи.
  Явная стабильная identity нужна, когда tag должен меняться с сохранением истории;
  fallback от ID сам по себе этого не гарантирует.
- Пустые `equipment`, `pipes` и `alarms` можно опускать в `project()`: конструктор
  материализует отдельные пустые массивы в проверенной модели. `reports`, `cables`,
  `hmis` и прочие дополнения также необязательны на границе автора.
- Название экземпляра и координаты `x/y` сейчас обязательны, в том числе для
  оборудования без собственного вида. Fallback названия на ID и независимое от
  модели автоматическое размещение требуют отдельного согласования с source editing.
- Единицы, тип значения, writable и ограничения портов описывают разные свойства.
  Они нужны для проверок; строковые `unit/dimension` не заменяют ещё незавершённую
  алгебру размерностей. `initial` не является показанием оборудования.
- В SQL-отчёте `schema` задаёт типы результата, `columns` — отображение, `signals` —
  зависимости/доступные источники. У этих полей разные задачи. Сокращать повторения
  можно helpers/defaults поверх того же плана, сохраняя типы, пропуски и coverage.
- Физическое соединение и binding протокола не дублируют друг друга. `bind()`
  возвращает новую ссылку на описание сигнала; потребители должны использовать эту
  ссылку, а не независимые объекты с одинаковым ID.

Этот аудит не меняет контракты исполнения, физических портов, отчётов или сборок.
