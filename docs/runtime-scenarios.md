# Сценарии симуляции через runtime API

Сценарий — обычный TS-файл инженерного проекта, импортированный в `project.ts`.
Его проверенное описание входит в тот же BuildArtifact, что оборудование и сигналы.
Изменение файла требует новой сборки и явного Publish/Apply. Воркер читает принятую
сборку из runtime database; текущую рабочую копию он не исполняет.

## Авторский файл

Например, `scenarios/command-response.ts` использует существующие сигналы проекта:

```ts
import { scenario, set, expectValue, wait } from '@saturn/core/scenarios';
import { motor } from '../equipment/motor';

export const commandResponse = scenario('command-response', {
  label: 'Проверка команды и обратной связи',
  timeoutMs: 15_000,
  steps: [
    set(motor.enabled, true),
    expectValue(motor.running, true, 5_000),
    wait(1_000),
    set(motor.enabled, false),
    expectValue(motor.running, false, 5_000),
  ],
});
```

В `project.ts` импортируйте этот файл и добавьте `scenarios: [commandResponse]`
в обычный `project({...})`. Пример предполагает уже объявленный `motor` с writable
boolean `enabled` и наблюдаемым boolean `running`; он не создаёт вымышленные
параметры оборудования. `set` выводит тип значения из Signal и требует writable.
`expectValue` проверяет точное равенство. `expectRange(signal, min, max, timeoutMs)`
принимает только числовой Signal и проверяет включительный диапазон по тем же правилам
качества и происхождения наблюдений.

Действия выполняются последовательно. `wait` использует реальное прошедшее время.
`advance(steps)` продвигает поддерживающий эту возможность драйвер на точное число
тактов. Время всей последовательности ограничено `timeoutMs` (до одного часа).
Checkpoint/reset и восстановление начального состояния пока не реализованы.
Повторный запуск сценария продолжает текущее состояние модели.

### Часы модели

Драйвер симуляции может объявить `Driver.simulation: SimulationClock`:

```ts
interface SimulationClock {
  state(): { readonly timeMs: number; readonly stepMs: number };
  advance(steps: number): Promise<void>;
}
```

Время — целые неотрицательные миллисекунды, шаг — положительное целое число.
Шаг фиксирован для установки; количество тактов в одном действии — 1–10000.
Драйвер выполняет интеграцию и ожидает публикацию своих наблюдений. Host не
синтезирует значения и не освежает их timestamps ради успешной проверки.
`advance` получает отмену через `DriverContext.signal`; реализация обязана её учитывать.

`POST /api/scenario/advance` получает `{expectedApplied, expectedRun,
expectedTimeMs, steps}`. Runtime проверяет начальное время внутри очереди команд,
а после выполнения — точное продвижение. Receipt хранит `clockBefore/clockAfter`.
Ошибочное продвижение запрещает последующие шаги этой установки до её замены;
фактические наблюдения остаются доступными, откат не имитируется.

Тесты подтверждают одинаковую траекторию тестового драйвера при разных задержках
реального времени. Детерминизм произвольной физической модели этим не подтверждается.
История сохраняет серверные `at`/`receivedAt`; драйвер передаёт модельные
миллисекунды в `sourceAt`. График задачи выбирает эту ось для пошаговой модели.
Агрегаты исторических отчётов пока интегрируют серверное время; из такого
интеграла нельзя выводить физический баланс ускоренной симуляции.

### Свежесть остановленной пошаговой модели

Активная установка с явным `SimulationClock` добавляет в runtime `Snapshot`
контекст `simulation: {run, build, timeMs, stepMs}`. Это полномочие host,
привязанное к конкретной установке; observation от plugin не назначает себе
чужие run/build или часы снимка.

Общее правило качества использует разницу `timeMs - sourceAt`, когда контекст
совпадает с provenance наблюдения. Пауза реального времени при неподвижных
часах модели не старит такое показание. Продвижение модели без новых
наблюдений старит его по модельному времени. `bad`, `offline`, исходное
`stale`, отсутствующее измерение и потеря браузерного соединения остаются
непригодными для проверки. Живые драйверы и симуляторы без явных модельных
часов продолжают использовать возраст от времени получения.

Контекст проходит тем же снимком через HTTP/SSE, проверку сценариев, Shell,
числовые readouts и приборы. Host не обновляет `at`, `receivedAt`, `sourceAt`
и не добавляет строки истории ради сохранения свежести. Завершение или замена
установки снимает полномочие её часов. Наблюдение следующего шага может
поступить до завершения `advance`; runtime подтверждает фактические часы после
выполнения и не выдаёт такое наблюдение за подтверждение будущего времени.

Plugin вправе наблюдать удерживаемые входы вместе с завершённым шагом, если
их состояние известно физической модели. Например, постоянная сила или
открытие идеального клапана остаются измеренными входами этого шага. Это
не автоматическое исключение всех writable-сигналов из проверки свежести.

Команда не подменяет измерение. Проверка проходит только по good/fresh sample с
provenance того же запуска и сборки. Она проверяет текущее наблюдаемое состояние;
это не отдельный протокол подтверждения конкретной команды устройством.

## Тот же воркер, что у отчётов

В конфигурацию зарегистрированного проекта `createWorkerHost` добавляется runtime:

```ts
projects: {
  'example/rig': {
    root: '/path/to/example',
    database: 'sqlite:///path/to/runtime/history.sqlite',
    runtime: {
      url: 'http://127.0.0.1:3100',
      token: process.env.SATURN_RUNTIME_CONTROL_TOKEN!,
    },
  },
}
```

Это серверная конфигурация. Токены не входят в TS-проект, BuildArtifact или тело
задания. Runtime URL задаётся администратором воркера, не отправителем задания.
`database` должна быть той же базой, которую использует настроенный runtime.
Standalone runtime host обслуживает этот API напрямую. В локальной IDE dev-host
создаёт worker по запросу и предоставляет браузеру same-origin gateway; внутренний
runtime token остаётся на сервере. Нужна постоянная база истории: `:memory:`
не разделяется с Bun Worker и показывает причину недоступности.

В Shell откройте **Мониторинг → Сценарии**. Здесь доступны список шагов применённой
сборки, запуск, отмена, время модели и результаты запусков. Checked-only сценарий
виден для чтения, запуск до Apply недоступен. Отличие исходников от Applied
показывается отдельно. Ошибка проверки сохраняет последнее наблюдавшееся значение.
Локальный gateway использует `/api/scenarios`, `/api/scenarios/start` и
`/api/scenarios/cancel`; изменения требуют обычный ключ сессии IDE.
Экран сценариев пока доступен в браузерной Shell. В терминале используется
клиент `scripts/run-scenario.ts`, описанный ниже; отдельного TUI экрана пока нет.

Получите контекст запуска:

```http
GET /api/scenario/state
Authorization: Bearer <runtime-control-token>
```

Ответ содержит `projectId`, `applied`, `run.id`, `mode`, `clock` и `snapshot`. Endpoint доступен
только активной simulation. Затем отправьте задание в существующий worker host:

```json
{
  "kind": "scenario",
  "project": "example/rig",
  "run": "experiment-001",
  "build": "<applied hash из runtime>",
  "scenario": "command-response",
  "expectedRun": "<run.id из runtime>"
}
```

Транспорт: `POST /api/jobs`, JSON, `Authorization: Bearer <worker-token>`.
Worker проверяет сборку, сценарий и запуск до постановки и перед исполнением.
Команды идут через `POST /api/scenario/command`; runtime проверяет `expectedApplied`
и `expectedRun` внутри той же очереди, что Apply. Даже восстановление прежней сборки
с новым запуском останавливает старый сценарий.

Готовый клиент в репозитории:

```sh
# SATURN_WORKER_TOKEN и SATURN_RUNTIME_CONTROL_TOKEN заданы в окружении.
bun scripts/run-scenario.ts http://127.0.0.1:3200 http://127.0.0.1:3100 example/rig command-response experiment-001
```

Клиент выводит ID задания, сборку, запуск и итоговый receipt. Он не выполняет Apply.
Управление заданиями использует существующие `GET /api/job?id=experiment-001.scenario`
и `GET /api/jobs?project=example%2Frig` с worker token.

## Ошибка, отмена и повтор

- В этом воркере одновременно допускается один queued/running сценарий на
  зарегистрированный проект. Отчёты продолжают использовать общую очередь и слоты.
  Это не глобальная блокировка ручных команд или других worker hosts.
- Повтор той же пары job ID/input возвращает receipt и не запускает команды заново.
  Другой input с тем же ID отклоняется. Для нового опыта нужен новый `run`.
- `POST /api/job/cancel` с `{"id":"experiment-001.scenario"}` отменяет queued job
  либо прерывает активные ожидания/HTTP-запросы. CLI также отправляет отмену по Ctrl+C.
- Отмена не откатывает уже принятые команды. При обрыве запроса команда могла
  исполниться; автоматического повтора нет. Отчёт о шагах различает завершённые
  шаги и шаг с ошибкой, сохраняет проверенные samples.
- Ошибка шага завершает последовательность; последующие команды не отправляются.
  Результат содержит wall-clock timestamps, build и telemetry run.
- После аварии worker process ранее running job получает `interrupted`; он не
  продолжается автоматически. Итоговый список шагов записывается при завершении
  работы worker; это не durable checkpoint каждого отдельного действия.

## Владение инженерной моделью

Состав объекта, параметры оборудования, физические уравнения, начальные условия,
2D/3D-представления, анимации и конкретные сценарии принадлежат инженерному проекту.
Примеры таких проектов размещаются в `saturn-examples` и используют обычные imports
публичного DSL. Saturn не выбирает поведение по ID проекта или типу станции.

Ядро предоставляет общие контракты сигналов, топологии, представлений, драйверов,
модельного времени и исполнения сценариев. Новая потребность примера расширяет
общий контракт; специализированная реализация остаётся в проекте. Достоверность
физической модели проверяется тестами и исходными данными самого проекта.
