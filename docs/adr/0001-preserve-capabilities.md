# ADR-0001 — Сохранение возможностей и границы новой реализации

Статус: принят. Дата: 2026-09-23.
Основание: запрос пользователя — новая архитектура должна взять лучшее старой, не сокращая
преимущества продукта, и закрепить структуру для дальнейшего развития.

## Решение

Наследуем семантику старого Saturn ADR-0008: один TS-проект, одно каноническое представление,
один runtime authority, проверенный неизменяемый build, раздельные source/published/applied,
исходники расширений принадлежат проекту. Прежние декларации не выдаём за нововведения.

Упрощаем реализацию через штатный Bun build/SQL и обычные imports, а не путём удаления
типизированных размерностей, оборудования, HMI, отчётов, replay или deployment boundaries.
Направления зависимостей закреплены в docs/architecture.md и executable import guard.

Source/bundle build находится в workspace. Runtime принимает проверенный artifact и не читает
рабочие исходники. Host связывает части. Shell обеспечивает непрерывный инженерный и операторский
сценарий, не дублируя модель. Одна команда запуска не означает обязательный один failure domain.

Новая модель артефакта получает версию v2, поскольку добавляет bundled driver и иной project shape.
Не допускаем молчаливой несовместимости под старой меткой v1. Миграция — отдельная проверяемая задача.

## Не принимаем

Полное переписывание работающей визуализации ради новой структуры; четыре встроенных вида
оборудования как окончательную модель домена; неявный deploy при сохранении live-проекта;
смешение исходников и historian в одной authoring model; framework плагинов/панелей/DI;
package-per-folder; фиктивные firmware/screenshots; тесты формы вместо тестов поведения.

## Последствия

Перенос функции остаётся открытым до выполнения соответствующего критерия в capabilities.md.
Маленький код с меньшими возможностями не объявляется улучшенной заменой. Текущий коммит
фиксирует структуру и часть исполняемых границ; он не объявляет завершённую parity или
готовность к промышленной эксплуатации.
