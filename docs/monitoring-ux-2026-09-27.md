# Производительность как инженерное наблюдение — 27 сентября 2026

## Референсы и собственное решение Saturn

Кадры Codex, присланные пользователем, показывают устойчивый каркас: глобальная
рейка → контекст проекта → рабочая область → вызываемая панель Review. [Описание
приложения Codex от OpenAI](https://openai.com/index/introducing-the-codex-app/)
также описывает проектный контекст и просмотр изменений внутри задачи. Изменения
интерфейса Codex именно за сегодняшний день не проверены живым просмотром:
автоматическая проверка отклонила доступ Computer Use к окну Codex. Этот документ
не приписывает текущему релизу детали, которых нет на пользовательских кадрах.

[Рекомендации Grafana](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices/)
предлагают вести от общего к частному, задавать конкретный вопрос панели и снижать
нагрузку на читателя. [Работа с dashboard](https://grafana.com/docs/grafana/latest/visualizations/dashboards/use-dashboards/)
показывает общий период и обновление; [переходы между панелями](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/manage-dashboard-links/)
сохраняют контекст времени. Для Saturn эти паттерны переводятся в вопросы инженера:
**какая версия объекта работает, какие измерения достоверны, где отклонение, и к
какому сигналу/источнику перейти для причины?**

Saturn не создаёт отдельный каталог метрик или ещё один dashboard store. Источник
панели — тот же проверенный `Project`, живой `Snapshot`, история и диагностика
runtime. Черновик проекта, Git, Checked, Published и Applied остаются различимыми.

## Иерархия экрана

1. **Контекст:** имя объекта, simulation/plant, Applied identity и фаза runtime;
   общий период, частота обновления и пауза **только отображения**.
2. **Ответ за несколько секунд:** активные тревоги, пригодные текущие сигналы
   из всех объявленных, работающие источники и ошибки записи архива. Ни один из
   этих счётчиков не называется «здоровьем системы» или uptime.
3. **Предметные группы:** project-owned мониторинговые правила по установке,
   агрегату или подсистеме. Группа сообщает `ok/warning/critical/unknown` на
   основании реальных измерений и качества, без вымышленного значения из
   `Signal.initial`. Если правил нет, доступны сами сигналы и их владельцы.
4. **Разбор:** выбранный числовой сигнал с настоящей историей за общий период,
   min/max, количеством наблюдений, интервалами пропуска и явным возрастом.
   Сигнал ведёт в уже существующие Properties/Source; источники — в отдельную
   таблицу диагностики. Разные единицы не накладываются на одну ось.

## Состояния и взаимодействия

| Состояние | Что показывает интерфейс |
| --- | --- |
| Нет Applied | Проверенная модель видна как контекст проектирования; панель не утверждает, что объект уже работает. |
| Нет measurement | Значение `—` и причина. `initial` не считается телеметрией. |
| Bad, stale, offline | Отдельные слова и возраст последнего receipt; числовой порог не превращает недостоверное измерение в `ok`. |
| Нет данных в периоде | Пустой график без соединяющей линии. Количество наблюдений не подменяет покрытие времени. |
| Ошибка history API | Последний полученный график помечен как старый; независимая диагностика источников остаётся доступной. |
| Пауза | Заморожен только вид; сбор и архивирование продолжаются, время снимка видно. |
| Нет связи с runtime | Не показывать зелёное «в реальном времени»; сохранённые значения не считаются текущими. |

На узком экране порядок: контекст → сводка → проблемные группы/сигналы → выбранная
история → источники. График сопровождается текстовыми min/max/count/quality и не
требует распознавать статус только по цвету. Поиск, выбор, period picker, пауза,
таблица источников и переход в инспектор должны работать с клавиатуры.

Индикатор Live требует работающего runtime с Applied-сборкой, активного драйвера
и доступной диагностикой. Открытый API сам по себе не подтверждает исполнение. Для суточной
истории архив загружается при выборе периода и затем только по явному действию
пользователя; часовая история опрашивается не чаще раза в минуту. Это ограничивает
повторные тяжёлые SQL-запросы при плотном архиве, но один длинный запрос всё ещё
может быть дорогим. Отдельные rollup/агрегаты для ML-потока пока не введены.

## Контракт расширений

Скопированный в проект модуль плагина может обычным `import` сформировать типизированные
правила мониторинга по уже существующим числовым `Signal`. Декларация входит в
`Project`/Checked artifact; общая чистая функция оценивает её по `Snapshot` и
`signalHealth`. Сигналы, история, тревоги и источники остаются каноническими;
скрытой установки плагина, выполнения произвольного кода в браузере и второго
runtime authority нет. Ошибка/неполнота одной группы не должна делать соседние
группы зелёными или скрывать их реальные измерения.

Это первый переносимый contract для порогов/качества, не полный старый extension
model, не вычисление любых derived expressions и не доказательство физической
безопасности. Хронологию событий поверх графика можно добавить после проверки
существующего alarm/history API; пустые фиктивные аннотации недопустимы.
