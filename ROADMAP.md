# Saturn roadmap

Обновлено: **2026-10-05**. Основание: создание и подключение проекта (ONB-1), текстовые decision-модели Jev/Kev (DEC-1), ACP-интеграция внешних coding agents, Saturn Mobile, совместная работа,
монтажа, пространственного контекста и проектирования по документам.

Это единый план развития Saturn IDE / Cloud / Mobile и интеграции внешних агентов. Пункты ниже —
**запланированные возможности**, а не заявление об их реализации. Закрывать пункт
можно только вместе с реализацией, проверками и ссылками на результаты.

Действующие границы задаёт [архитектура](docs/architecture.md), обязательства переноса —
[матрица возможностей](docs/capabilities.md), область уже описанных проверок —
[verification](docs/verification.md). Этот roadmap дополняет их, не отменяет незавершённый
перенос и не меняет архитектурный контракт одним лишь появлением задачи.

## ARCH-1 — владение кодом между репозиториями

Приоритет **P0**, выполнено 2026-10-05. Рефакторинг не вводит новые пакеты или
runtime-слои; он удаляет исторические обратные зависимости и фиксирует существующую
архитектуру автоматическими проверками.

- [x] `saturn-ide` владеет DSL/core, build artifact, workspace, runtime, Shell и local host.
  Production source больше не предполагает соседний checkout `saturn-examples`;
  внешние demo/example projects передаются явно.
- [x] `saturn-examples` — канонический владелец завершённых authored engineering projects.
  Architecture check запрещает runtime-импорты IDE/SaaS implementation и sibling plugin source.
- [x] `saturn-plugins` — канонический владелец project-owned source kits. Широкий
  development alias `@saturn/core/*` удалён; допустимы только объявленные public core exports.
- [x] `saturn-saas` больше не хранит копию pumping-station. Для пустого проекта используется
  `saturn-ide/project-template`, для демонстрационного — immutable revision из
  `saturn-examples` по provenance. OAuth/server не исполняет этот source.
- [x] Во всех четырёх репозиториях добавлены/усилены architecture checks, чтобы границы
  проверялись CI, а не оставались договорённостью в документации.

## Направление продукта

**Saturn Mobile — новое поколение средств разработки: вайбинженеринг.**
Инженер описывает намерение, работает с живой моделью голосом, текстом и прикосновениями,
совместно с участниками проекта и выбранным внешним агентом проверяет результат и подготавливает
изменение программной части инженерного объекта. Телефон — полноценная среда этой работы,
а не только просмотрщик уведомлений или уменьшенная desktop IDE.

Одна типизированная инженерная модель связывает исходники, оборудование, топологию,
сигналы, HMI, отчёты, среды исполнения и наблюдения. Человек выражает инженерное решение
один раз; повторный перенос уже известного смысла между независимыми настройками
должен исчезать. Агент использует эти связи, а не вручную обслуживает несколько моделей.

**Ближайший приоритет — коллаборация участников и внешних агентов через ACP.** Камеры и видеорегистраторы
подключаем как существующие источники наблюдения. Непрерывная запись и основной архив
остаются на их стороне. Коллаборация не ждёт собственного видеосервера, полного BIM
или сложной 3D-модели здания.

## Неизменные границы

- Один authored TypeScript project; оборудование, диаграммы и AI не получают отдельные
  редактируемые Project/Signal/Topology. Всю систему разрешено описать в одном файле
  или разделить обычными imports: правила «один файл — один прибор» нет.
- Голос, чат, drag и исходники изменяют один проект через общие типизированные операции.
  Новый публичный примитив вводится вместе с работающим сценарием, а не каталогом
  сущностей на будущее. Существующие equipment/ports/signals/presentation переиспользуются.
- Source, checked, published, applied и наблюдаемое состояние различимы.
  Сообщение «я подключил», ответ устройства, визуальное наблюдение и инженерная проверка
  сохраняют своё происхождение. Applied revision не доказывает правильность монтажа;
  confidence агента не заменяет доказательство. Это разные измерения, не лестница истины.
- Разработка, публикация, оперативное управление, просмотр видео и передача кадров агенту
  имеют отдельные полномочия. Переключение роли или вида интерфейса не меняет права.
  Открытие чата не выдаёт агенту runtime credentials, shell или полномочия apply.
- Обсуждение, alarm, команда и изменение проекта имеют собственные жизненные циклы.
  Закрытие обсуждения не квитирует alarm; согласие в сообщении не применяет сборку.
- Live-команды проходят runtime authority с проверкой среды, актуальной applied revision,
  прав и результата. Неоднозначный ответ не ретраится как обычное сообщение.
  Replay, симуляция и восстановление мобильной связи не отправляют команды объекту.
- Общая дизайн-система и domain-компоненты используются в Shell, чате, карточках событий,
  отчётах и HMI. UI агента не должен становиться отдельным продуктом.

## Порядок и зависимости

Сначала закрывается один сквозной сценарий совместной работы. Расширения добавляются
к тому же основанию; даты релизов и неподтверждённые оценки сроков здесь не назначаются.

| Этап | Результат | Зависимости |
| --- | --- | --- |
| COL-1 | Участники, долговременные обсуждения, точные ссылки на контекст | Существующая модель ресурсов; серверная авторизация |
| COL-2 | Совместные сеансы, присутствие, показ на дисплеях | COL-1; текущие представления Shell |
| AGT-1 | ACP-клиент: Codex/Claude/другой внешний агент работает с Saturn-контекстом без собственного agent harness | COL-1; workspace/AST/check; MCP/tool boundaries |
| MCP-1 | ChatGPT/Codex получают read-only инженерный контекст Saturn через существующую runtime/model семантику | runtime read API; SaaS gateway; AGT-1 tool boundaries |
| MOB-1 | Единый мобильный Shell для iOS/Android, операторов, инженеров и бизнеса | COL-1; AGT-1 для разработки; Presentation/replay для соответствующих видов |
| FIELD-1 | Голосовая работа при монтаже и пусконаладке | COL-2, AGT-1, MOB-1; реальная диагностика runtime |

Базовый mobile web, domain-карточки и read-only интеграцию камеры можно делать параллельно
с коллаборацией. Для первого сценария достаточно ссылки на оборудование и изображения:
не нужно блокировать его на нативных сборках, голосе, документах или 3D-здании.
Незавершённые Presentation, replay, typed reports и runtime isolation из матрицы возможностей
остаются явными зависимостями, а не объявляются готовыми этим планом.
Общий authoring различает неактивные сущности `//` и явные концы `free()`: сцена редактора
не входит в BuildArtifact и не применяется. Схема артефакта остаётся `saturn.build@2`.

## COL-1 — участники, обсуждения и общий контекст

Владелец: общие контракты ресурсов и отображения в IDE; идентичность, членство,
долговременное хранение и доставка в Cloud/integration layer.

- [ ] Ввести идентичность участника Saturn с привязками к провайдерам входа. Приглашать
  инженера, оператора, монтажника и заказчика без обязательного доступа к GitHub-репозиторию.
  Существующие GitHub-права сохраняют независимое действие и не маскируются UI.
- [ ] Поддержать обсуждения проекта и задачи с несколькими участниками, упоминаниями,
  передачей задачи и явной областью доступа. Один разговор может ссылаться на несколько
  устройств; у одного устройства может быть несколько разговоров.
- [ ] Заменить историю одной вкладки долговременными сообщениями и событиями с server-assigned
  авторством, идентификаторами, временем, идемпотентным приёмом, восстановлением после reconnect
  и состоянием прочтения. Человек, запуск агента и результат действия различаются.
- [ ] Зафиксировать ссылку на ресурс вместе с контекстом отправки: project, environment,
  revision, entity/selection, view, момент истории и доступный снимок наблюдения.
  Переименование, удаление или последующее выделение не должны переадресовывать старое «здесь».
- [ ] Прикреплять оборудование, сигнал, участок чертежа, кадра, интервал видео/тренда,
  HMI, документ, alarm, отчёт и предложение изменения через общие ссылки. Отметка на фото
  остаётся отметкой, пока её соответствие оборудованию не установлено.
- [ ] Проверять права на сообщения, вложения, связанные ресурсы и подписки на сервере,
  включая отзыв доступа. Приглашение в thread не открывает весь проект. Агент не пересказывает
  общему кругу сведения, доступные только одному участнику; публикация вовне явная.
- [ ] Построить Inbox и доставку упоминаний/alarms/отчётов из сохранённых событий: очередь,
  повторы с дедупликацией, настройки адресатов и deep links. Доставка не требует запуска LLM;
  недоставленный push не считается подтверждением alarm или гарантированным оповещением.

**Приёмка:** два разных пользователя открывают одно обсуждение на разных устройствах;
после закрытия клиента и переподключения видны те же сообщения и исторические ссылки.
Повтор запроса не создаёт вторую запись. Отозванный участник теряет чтение и подписку.
Обсуждение неисправности, её alarm и исправляющее изменение не закрывают друг друга автоматически.

**Приёмка:** монтажник выделяет AI3 на телефоне, инженер переходит к тому же входу в IDE,

## AGT-1 — внешние агенты через ACP

Владелец Saturn: тонкий ACP client host и существующий workspace. Выполнение агента,
модель, auth, billing, native tools и конфигурация принадлежат внешнему agent harness.

Решение 2026-09-28 после проверки официального ACP TypeScript SDK и реализации Zed:
использовать **stable ACP v1** и официальный `@agentclientprotocol/sdk`; experimental v2
не нужен. Не реализовывать свой JSON-RPC, registry, model gateway, conversation store или
agent-specific DSL.

- [ ] Первый вертикальный сценарий — внешний ACP-процесс запускается в корне текущего проекта.
  Его обычные правки TypeScript подхватываются уже существующими watcher → check/build →
  Diagram/HMI/runtime-preview. Отдельный agent workspace/AST/store запрещён.
- [ ] Saturn показывает thread/update/tool events и ACP permission request; разрешение всегда
  остаётся явным пользовательским действием. Auth/login/model/config остаются нативными для
  Codex/Claude/другого агента.
- [ ] Использовать официальный ACP Registry для известных агентов и форму `command/args/env`
  только для custom agent. Не создавать собственный каталог пакетов или installer protocol.
- [ ] Не вводить MCP ради редактирования файлов. Добавлять Saturn MCP tools только там, где
  производная инженерная семантика уже существует в core и действительно полезнее чтения source:
  например inspection/impact/diagnostics. MCP не получает runtime command/apply authority автоматически.
- [ ] Review остаётся текущим lifecycle Saturn: source diff → check → Git → publish → apply.
  ACP session и успешный tool call не являются checked/published/applied revision.

**Приёмка:** инженер выбирает внешний Codex или Claude, агент меняет обычный TypeScript текущего
проекта, Saturn без второго model store показывает ту же правку в Source и соответствующей проекции.
Permission виден до действия. Ошибка/отмена агента не меняет applied runtime. После закрытия процесса
не остаётся дочерних agent-процессов. Повторное подключение использует ACP session capability, если
её поддерживает конкретный агент; Saturn не подменяет её собственной историей.

## Разделение ответственности и хранения

| Слой | Ответственность |
| --- | --- |
| IDE core / workspace | Канонические ресурсы и ссылки; обычный TS; AST/import/change operations, версии, check и проектные артефакты |
| IDE Shell / host | Общие domain-компоненты, поверхности, selection/view intents, присутствие, mobile/local composition и adapters |
| Runtime | Наблюдения, quality/time, команды, alarms, история и applied authority; работа не зависит от открытого чата |
| Cloud / saturn-saas | Identity, членство, обсуждения, durable storage, доставка/уведомления, sessions, выполнение агента и инфраструктурные adapters |
| saturn-plugins / project source kits | Камеры/протоколы, внешние форматы документов и геометрии, device/target implementations без global registry |
| saturn-examples | Воспроизводимые проекты и сквозные сценарии с фактическими результатами проверок |

IDE не импортирует SaaS, GitHub OAuth, AI Gateway, конкретную VMS или библиотеку доставки
как доменную зависимость. Без подключённого AI и Cloud локальные проект и runtime сохраняют
свои возможности. Контракты коллаборации не вводят второй runtime authority.

| Данные | Хранение / срок жизни |
| --- | --- |
| Authored модель, исходники, сохранённые виды | Проект / Git |
| Обсуждения, сообщения, предложения, ссылки и квитанции | Долговременное хранилище коллаборации; ссылки на authoritative runtime events |
| Присутствие, курсоры, ракурсы, preview жестов | Временное состояние сеанса с истечением |
| Telemetry, команды и история исполнения | Runtime/history с собственным provenance |
| Непрерывное видео и основной архив | Существующие камеры / NVR / VMS |
| Загруженные документы и явно сохранённые evidence clips | Отдельное защищённое хранилище с доступом/retention; в проекте ссылки и версии |

Chat SDK рассматривается как интеграционный адаптер каналов, AI SDK — адаптер модели,
AI Elements — UI primitives. Их служебные user/assistant/tool roles и state не заменяют
идентичность участников, историю Saturn или проверку capabilities. Конкретный media transport,
мобильный host и механизм совместного текста выбираются при реализации соответствующего
сценария; roadmap не фиксирует неподтверждённую совместимость библиотек.

## Первый сквозной результат и дальнейшая демонстрация

**Первый вертикальный срез:** монтажник на мобильном web выделяет вход PLC в обсуждении;
инженер открывает эту же ссылку в браузере; Agent объясняет доступное наблюдение и предлагает
проверяемое изменение. Диагностика показывается на зарегистрированном мониторе. К обсуждению
прикладывается разрешённое наблюдение существующей камеры/эмулятора с честным указанием источника.
На следующий день контекст, участники, решение, проверки и реальное состояние изменения
восстанавливаются из сохранённых данных.

**Расширение демонстрации:** чертёж + I/O-list + фото → DSL draft → настоящие 2D/3D и HMI →
голосовое уточнение при монтаже → проверка сигнала → согласованное изменение → отдельный
разрешённый apply → alarm → push оператору → совместная диагностика/replay → бизнес-отчёт
по тому же событию. Для каждого перехода показываются среда, версия, источники и ограничения.

Демонстрация и познавательная документация используют настоящие компоненты Saturn,
рендеры и результаты. Сгенерированная картинка, мок ответа или наличие тестового файла
не являются доказательством работы продукта.

## Правила закрытия этапов

У каждого закрытого пункта должны быть commit/implementation reference, воспроизводимый
сценарий, фактически выполненные проверки с указанным host/runtime и результатом, а для
визуального/мобильного поведения — реальные кадры/видео и оценка UX. Не запускать формальную
галочку только потому, что код скомпилировался.

Проверять не только happy path: конфликт правок, отзыв прав, недоступный источник,
устаревшее значение, разрыв связи, повторную доставку, неверную среду/revision, ошибку агента,
неполный replay и независимость runtime от отказа Cloud/чата. Изменение без источника или
неподтверждённый physical outcome остаются явно непроверенными.

## Что намеренно не входит в ближайший объём

Собственный NVR и непрерывный видеоархив; обязательный полный BIM/CAD; VNC как основа
просмотра операторского HMI; обязательный CRDT или распределённый event-sourcing для всей
системы; дублирующая инженерная модель внутри чата; скрытая выдача прав агенту; автоматическое
применение по голосовой реплике; выдача уверенности модели/кадра эмулятора за факт физической
проверки. Эти ограничения не сокращают существующие обязательства матрицы возможностей.

## DEC-1 — текстовые решения Jev/Kev, 2026-09-29

По отдельному запросу добавлен ограниченный decision adapter для существующих действий
Shell. Это не замена AGT-1, не новый генеративный model gateway и не собственный agent harness.
Текстовый запрос → выбор существующей команды → последовательное уточнение аргументов →
предпросмотр → явное подтверждение → тот же CommandShell и браузерная ShellSession.

Реализация: `src/core/decision.ts`, `src/host/decision-api.ts`,
`src/shell/model/decisions.ts`, `src/shell/decision-panel.tsx`.
Подключение и границы: [текстовое управление](docs/decision-control.md).
Используется общий TypeSafe System One choice API: локальный/удалённый Kev,
TypeSafe Jev, TypeSafe-compatible маршрут Vercel AI Gateway или собственный endpoint.
Конфигурация и ключ находятся на host; автоматический cloud fallback отсутствует.
Без модели обычный Shell и runtime сохраняют работоспособность.

В предложении видны project, mode, applied и точная команда. Смена ввода, выделения,
версии/среды или dirty draft отменяет старое решение. Guard повторяется перед выполнением,
план одноразовый с TTL; автоматических повторов команд и выдуманного readback нет.
Save/command/ack сохраняют существующие workspace/runtime authority. Произвольный код,
физические source-операции, publish/apply и речь не включены в этот текстовый срез.

Приёмка интеграции вынесена в `tests/decision-api.test.ts`, `tests/decisions.test.ts`
и `scripts/decision-browser-test.ts`; последний входит в основной CI и сохраняет
desktop/mobile кадры. Результаты конкретной ревизии проверяются в GitHub Actions:
наличие теста и успешный ответ детерминированного API не доказывают качество живой модели.

Остаётся открытым: реальный корпус русских запросов Saturn и измерение качества Jev/Kev;
подготовка/проверка/подтверждение физических source-операций через общий authoring planner;
совместные durable approvals и права Cloud; голосовой transport поверх того же сеанса.
Не закрывать COL-1, AGT-1, MOB-1 или FIELD-1 только на основании этого адаптера.
